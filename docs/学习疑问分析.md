# 自主学习与资料分析：状态已更新，界面为什么不刷新？

> 目标四素材 · 撰写人：本人（独立完成） · 资料核查日期：2026-11-15
> 本文记录开发过程中真实遇到、定位、修复并复验的一个问题，不是摘抄式资料罗列。

## 1. 疑问的由来（真实现象）

在模拟器上跑《雾灯档案》首轮联调时，我按「先去借阅台查记录」完成 E01：顶部 `HeaderBar` 立刻从「线索 0/9、事件 0/14」变成「线索 1/9、事件 1/14」，说明 `CaseViewModel.choose()` 已经算完并落盘；但下方 E01 卡片的**两个选项按钮仍然可点**，而本应解锁的 E02 却看不到选项。另一个现象出现在推理页：点击「社长 / 改评优名单 / 21:40 人为拉闸」后，三项断言背景仍是白色，没有琥珀色选中态——可最终提交却正确进入真相结局，证明 `this.hypothesis` 的值确实被保存了。

也就是说：**业务状态是对的，UI 呈现是旧的**。这两处如果不修，评分项「页面与交互体验」「操作结果反馈清晰」会直接失分。

## 3. 定位过程

**第一步，排除业务层。** 我在 `CaseEngine.applyChoice()` 里加了可断言的返回结构，并用 T01 单测验证 `journal +1`、`clues` 含 C1、`deriveStage` 由 BRIEFING 变 SEARCH；同时模拟器控件树显示头部计数确实变化。因此引擎、ViewModel、Preferences 都是对的。

**第二步，怀疑 @State 刷新。** 对照资料 3，检查 `ExploreView.reload()`：它把 `this.state`、`this.cards` 都赋了新数组/新对象引用，符合"整体重新赋值触发刷新"的要求；而 `HeaderBar` 的刷新也证明 `AppStorage` 广播生效。所以问题不在 @State 本身，而在**子组件是否被重建**。

**第三步，查 ForEach 的 key。** 当时的代码是：

```ts
ForEach(this.cards, (card: EventViewData) => {
  EventCard({ eventId: card.eventId, available: card.available, ... })
}, (card: EventViewData) => card.eventId + ':' + card.body.length.toString())
```

E01 完成后，`eventId` 不变、`body` 长度不变 → **key 不变**。按资料 1，key 不变时框架复用旧组件，不"视为替换并创建新组件"，于是 `EventCard` 的 `@Prop available` 停留在旧值 true，选项继续渲染。这与官方"建议使用与 UI 相关的数据属性作为键值"的建议正好相反——我的 key 恰好漏掉了唯一变化的 UI 相关字段。

**第四步，查推理页的 @Builder。** 当时 `selectorBlock(title, options, selected, group)` 把 `selected` 当作**普通值参数**传入。@Builder 的普通参数不具备响应式能力，`this.hypothesis` 变化不会让这个参数重新求值；而 `saveHypothesis()` 确实把新值写进了 `@State` 与 Preferences，所以功能对、视觉错。

## 4. 结论与修复

| 问题 | 修复 | 依据 |
|---|---|---|
| 事件卡片选项不消失 | `ForEach` 的 key 改为包含全部影响 UI 的字段：`eventId + available + completed + choiceIds + body.length`，状态变化即产生新 key，框架重建子组件 | 资料 1、2 |
| 线索板「已获得」不刷新 | key 改为 `clue.id + 已获得线索数`，线索集合变化时整批重建 | 资料 1 |
| 推理页选中态不高亮 | 新增 `selectedOf(group)` 私有方法，**在 @Builder 内直接读 `@State hypothesis`**，不再用值参传 `selected`；key 同步加入选中值 | 资料 3 |
| 验证结果看不到 | 把「证据链已闭合 / 尚未闭合」结果卡从按钮下方移到按钮**上方**，点击「验证推理条件」后在原滚动位置即可看见 | 交互可用性 |

修复后重新执行 `assembleHap`（BUILD SUCCESSFUL）、重装 HAP，并用 `uitest dumpLayout` + `snapshot_display` 复验：E01 卡片变为「已查阅」且选项消失，E02 出现「逐页核对值日证」；推理页三项断言呈琥珀色高亮，结果卡显示「证据链已闭合」。对应截图为 `docs/figures/fig6-1-b-explore-events.jpeg`、`fig6-1-e-verdict.jpeg`、`fig5-2-boundary-verdict.jpeg`。

## 5. 为什么选这个方案，而不是直接迁移 V2

资料 4 提示 `@Param` 是引用传递、V2 配合 `@Trace` 可做深度观测，看起来能"根治"。但我核对了 `docs/新技术认识.md` 中的版本与限制后判断：本项目 `GameState` 是 `interface` + 白名单反序列化的纯数据对象，迁 V2 需要把整条 JSON 校验链改成 `new` 出来的类实例；且 V1→V2 混用接口（API 19+）对整体重新赋值有额外调用要求，与本项目 SSOT 写法冲突。**最小、可验证、不破坏可测性的修复**是让 key 与响应式读取符合 V1 的既有契约，因此选择前者，把 V2 迁移列入后续学习计划。

## 6. 这次排查留下的工程约定

1. `ForEach` 的 key 必须包含所有参与渲染计算的状态字段，禁止只用业务 id。
2. `@Builder` 的普通参数一律当常量用，动态选中态必须直接读 `@State`。
3. UI 问题先用「业务断言 + 控件树 + 截图」三层证据定位，不凭猜测改业务代码。
4. 每次触及状态渲染逻辑，重新跑 12 条 Local Unit Test 并在模拟器复验关键页面。
