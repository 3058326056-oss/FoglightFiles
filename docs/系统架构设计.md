# 《雾灯档案》系统架构设计

> 依据 `docs/软件需求说明书.md` 第 5 章冻结契约产出 · 独立完成 · 与源码逐项对应
> 架构图见 `docs/figures/fig2-1-system-architecture.svg|png`，业务流程图见 `docs/figures/fig3-1-business-flow.svg|png`

## 1. 架构目标与总体视图

本作品是**单机、离线、可存档恢复**的校园推理 App。架构要解决三件事：

1. 剧情分支必须**真实改变后续事件**，而不是文字跳转 → 用"数据目录 + 纯函数引擎 + 显式状态效果"表达；
2. 杀进程后进度、日志、结局必须**逐项恢复** → 唯一权威状态 `GameState` 整体持久化；
3. 核心业务逻辑必须**可被单元测试直接验证** → 纯逻辑层零 `@ohos.*` 依赖。

因此采用 MVVM + 分层架构，自上而下五层：

| 层 | 模块 | 依赖系统 API |
|---|---|---|
| 表示层 M6 | `Index.ets` + 6 个视图 + 3 个组件 | 是（ArkUI） |
| 状态编排层 M5 | `CaseViewModel` / `AppContext` / `UiBus` | 否 |
| 纯业务逻辑层 M1/M2 | `CaseEngine` / `Models` / `CaseCatalog` | **否（强制）** |
| 数据持久层 M4 | `IStateRepository` / `StateRepository` / `InMemoryStateRepository` | 仅生产实现 |
| 入口与测试 M6/M7 | `EntryAbility` / `EntryBackupAbility` / 12 条 Local Unit Test | 是 / 否 |

分层的关键是**依赖方向单向向下**：界面不写业务判断，引擎不认识 UI 与 Preferences，仓储通过接口注入 ViewModel。图2.1 中每个模块都标注了「本人负责」（独立完成，无组队）。

## 3. 关键模块接口（与需求说明书 5.2 一致）

### 3.1 `CaseEngine`（纯函数，不修改入参）

| 方法 | 输入 | 输出 |
|---|---|---|
| `checkAvailability` | `GameState, EventNode` | `Availability { available, missingClues, missingFlags, blockedBy, reason }` |
| `availableEvents` | `GameState` | `EventNode[]` |
| `resolveBody` | `GameState, EventNode` | `string`（`altFlag` 命中返回 `altBody`） |
| `availableChoices` | `GameState, EventNode` | `Choice[]` |
| `applyChoice` | `state, eventId, choiceId, now, entryId` | `ChoiceResult { accepted, state, journalEntry, gainedClues, unlockedEvents, message }` |
| `validateHypothesis` | `GameState, Hypothesis` | `Verdict { ready, errors, missingClues, matchedClues, hint }` |
| `resolveEnding` | `GameState, Hypothesis` | `Ending`（固定优先级，结果唯一） |
| `deriveStage` / `getProgress` | `GameState` | `Stage` / `Progress` |

`now`、`entryId` 由调用方注入，引擎内部不取系统时间、不取随机数、不落盘；因此同一输入必得同一输出。

### 3.2 `IStateRepository`

```text
load(): Promise<GameState>          // 空串→新案；损坏→备份原串后回落新案；不抛异常
save(state): Promise<void>          // 克隆 + 日志裁剪 → put + await flush
clearAll(): Promise<void>           // 写入一枚全新案件
readBackup(): Promise<string>       // 最近一次解析失败的原始串
```

生产实现 `StateRepository` 是全工程**唯一**引用 `@kit.ArkData` 的位置；`InMemoryStateRepository` 让单测完全脱离设备。

### 3.3 `CaseViewModel`

`restore / choose / selectScene / setHypothesis / submitVerdict / restartCase / flush / getState / getProgress / getAvailability / getBody / getChoices / getSceneEvents / getVerdict / getEnding`。所有写状态路径遵循「同步改内存 → `await` 串行落盘」，写盘失败不阻断内存态与 UI，`onBackground` 再兜底 `flush()`。

## 4. 关键时序

### 4.1 一次选择（图3.1 主链路）

```text
ExploreView.onChoose(eventId, choiceId)
  → CaseViewModel.choose()
      → CaseEngine.applyChoice(state, …, clock(), idGen())   // 纯函数，返回新 GameState
      → this.state = result.state（SSOT 更新）
      → await persistNow() → repo.save() → Preferences put + flush
  → 结果反馈条（选项结果文案 + transition 过渡）
  → bumpVersion() → AppStorage('stateVersion') +1
      → Index / BriefView / ExploreView / ClueBoardView / JournalView 的 @StorageLink + @Watch 各自 reload
      → @State 整体重新赋值 → ArkUI V1 重绘
```

### 4.2 冷启动恢复

```text
EntryAbility.onWindowStageCreate
  → AppStorage.isReady = false；loadContent('pages/Index')（只渲染加载态）
  → void bootstrap() → 装配 StateRepository / CaseEngine / CaseViewModel
  → await vm.restore() → repo.load() → sanitizeGameState 白名单校验
      ├─ 通过 → hydrate 真实状态（含 endingId，直接渲染结局页）
      └─ 失败 → 原串写 game_state_backup → createNewCase → Toast「存档异常，已重新开局」
  → AppStorage.isReady = true → Index 一次性 syncFromModel → 渲染业务页
```

`await restore()` 完成前不渲染业务内容，避免默认新案闪现或被回写覆盖存档（需求说明书 EX-04 / B5）。

### 4.3 结局判定

`validateHypothesis` 先验证三项断言 + `C5/C7/C8` + `timeline_fixed`；`resolveEnding` 按固定优先级返回唯一结局：指认对象错误 → `END_MISJUDGE`；证人改口 → `END_COVER`；完整证据链 → `END_TRUTH`；其余 → `END_PARTIAL`。判定不依赖数组遍历顺序，可被 T05/T06/T07 精确锁定。

## 5. 关键设计决策与理由

| 决策 | 理由 | 代价 / 局限 |
|---|---|---|
| 剧情数据全部是本地常量目录（`CaseCatalog`） | 离线可复现、可单测、无需 AI 或服务器；事件门槛与 effects 是分支的唯一实现依据 | 新增剧情需改代码并发版 |
| 引擎零系统依赖 | `entry/src/test/` 可直接 import；12 条用例无需设备 | 时间/id 必须由调用方注入 |
| `GameState` 整体 JSON 存 Preferences | 单一文档型状态，无联表查询需求；`flush()` 简单可靠 | 日志增大后序列化占主线程 → 120 条 FIFO 上限；后续可迁 RDB 分页 |
| `AppStorage` 版本号广播 | 六个视图共享同一份 SSOT，避免层层 `@Prop` 深拷贝 | 需遵守 `ForEach` key 与 `@Builder` 响应式约束（见学习疑问分析） |
| 状态管理统一 V1 | 与纯数据对象 + 白名单反序列化最契合；避免 V1/V2 混用隐性风险 | 深层观测需整体重新赋值；V2 迁移列入持续学习计划 |
| 白名单反序列化 `sanitizeGameState` | 禁止直接 `as GameState` 信任 `JSON.parse`，目录外 id / 非法 trust / 版本不符一律回落 | 新增字段必须同步更新校验与 schemaVersion |
