# 新技术认识：ArkUI 状态管理 V2 与 V1/V2 混用

> 目标四素材 · 撰写人：本人（独立完成） · 资料核查日期：2026-11-15
> 本作品实际采用状态管理 V1；本文记录对 V2 的用途、适用版本与局限的核查结论，以及选型理由。

## 1. 为什么关注这项技术

《雾灯档案》的状态主体是一份 `GameState`：包含 9 条线索 id、20 个分支 flag、14 个已完成事件、最多 120 条日志以及一份可空的判断对象。每次选择都会产生一份**新状态**，六个页面要同时刷新。开发中最棘手的问题正是"状态变了但界面没变"（详见 `docs/学习疑问分析.md`），因此我系统核查了 ArkUI 状态管理 V1 与 V2 的能力边界。

## 2. 用途

状态管理 V2 的核心能力是**对类对象属性的深度观测**：`@ObservedV2` 装饰类、`@Trace` 装饰需要观测的属性，属性变化时只通知与该属性关联的组件刷新，而不必整体重建组件树。官方文档明确指出 V1 无法直接观测嵌套类对象的属性变化，V1 需要用 `@Observed` + `@ObjectLink` 逐层拆分自定义组件，层级较深时代码复杂度明显上升；V2 用 `@Trace` 直接解决这一痛点。此外 V2 提供 `@Local`、`@Param`、`@Once`、`@Event`、`@Monitor` 等装饰器，把"单向传参、双向同步、变化监听"拆得更细。

对本项目而言，若把 `GameState` 改造成 `@ObservedV2` 类，理论上可以让"线索数 +1"只刷新线索板与进度条，而不必让探索页整列重建。

## 3. 适用版本（可核查）

| 能力 | 起始 API 版本 | 依据 |
|---|---|---|
| `@ObservedV2` / `@Trace` | **API version 12** 起支持；同版本起支持 ArkTS 卡片与元服务 | 华为开发者联盟《@ObservedV2装饰器和@Trace装饰器：类属性变化观测》 |
| V1 → V2 混用 `UIUtils.enableV2Compatibility` | **API version 19 及之后** | 华为开发者联盟《状态管理V1和V2混用指导(API version 19及之后)》 |
| `@State` 支持 ArkTS 卡片 / 元服务 | API 9 / API 11 | 华为开发者联盟《@State装饰器：组件内状态》 |
| `@Prop` | API version 7 起（卡片 API 9、元服务 API 11） | OpenHarmony 官方 API 参考 `ts-state-management-prop.md` |

本工程 `build-profile.json5` 冻结为 `compatibleSdkVersion 6.1.1(24)`、`targetSdkVersion 26.0.0`。官方《应用兼容性说明》给出的版本大小关系为 `26.0.0 > 6.1.1(24) > …`，且要求 `compatibleSdkVersion ≤ targetSdkVersion ≤ compileSdkVersion`。因此 **API 12 的 V2 装饰器与 API 19 的混用接口在本工程的最低兼容版本 24 上均可用**，并不存在"版本不够"的问题；是否迁移纯粹是工程取舍，而不是能力限制。

## 4. 局限（这是本文的重点）

1. **V2 不是"自动更灵敏"，而是另一套契约**：`@ObservedV2` 与 `@Trace` 必须成对使用，单独一个不起作用；被装饰的类必须经 `new` 实例化才具备被观测能力；未被 `@Trace` 装饰的属性在 UI 中无法感知变化。本项目大量使用 `interface` + 对象字面量与 `JSON.parse` 白名单重建（`sanitizeGameState`），若迁到 V2，需要把整条反序列化链改造成类实例构造，反而削弱"纯数据、易序列化、易单测"的优势。
2. **V1/V2 混用有明确禁区**：官方混用指导列出的限制包括"不支持非 object 类型""不支持 `undefined`、`null`""不支持非 V1 状态变量数据"；并建议 `enableV2Compatibility` 在 V2 组件的构造处调用，否则当变量被整体赋值时需要再次手动调用。本项目的 `CaseViewModel` 恰恰采用"整体重新赋值新对象引用"的写法，与"整体赋值后需再次调用"的要求相冲突，混用会引入隐性刷新风险。
3. **V1 的一级观测限制**：`@State` 只能观测其直接绑定的 UI，复杂对象需要新引用才会触发刷新；`@Prop` 对复杂类型是**深拷贝**，父子组件之间并不共享同一份对象。本项目因此采用 `CaseViewModel` 单例持有唯一权威状态、页面按版本号广播后各自 `getState()` 取副本的 SSOT 模式，而不是层层传 `@Prop`。
4. **V2 与工程工具链的适配成本**：本工程使用状态管理 V1 + Stage 模型 + `@ohos/hypium` Local Unit Test，纯逻辑层零 `@ohos.*` 依赖；若 UI 层改用 V2，需要同步核对 `@ComponentV2` 与 `ForEach`、`Tabs`、`@StorageLink` 的组合行为，回归成本高于本次收益。

## 5. 本作品的选型结论

- **本期统一使用状态管理 V1**，并把约束写进需求说明书附录 B（B6）：每次状态变更后整体重新赋值新对象引用，禁止直接改对象属性；`@Builder` 的普通参数不作为响应式数据使用；`ForEach` 的 key 必须包含会影响 UI 的状态字段。
- 通过 `UiBus` 的 `AppStorage` 版本号广播 + 各页面 `@StorageLink/@Watch` 重新拉取 SSOT，规避 V1 深层观测不足的问题，且让纯逻辑层保持可脱离设备单测。
- 把 V2 迁移列为后续具体学习任务，见 `docs/持续学习计划.md`。
